# معماری فنی Vitalis — Clinical Eldercare Operations Platform

> نسخه: v0.1 (طراحی اولیه) | تاریخ: 1405/05/03

## ۱. اصول طراحی

1. **Care Timeline به‌عنوان هستهٔ محصول.** هر رکورد (علائم حیاتی، دارو، یادداشت مراقبتی، حادثه، تحویل شیفت) روی خط زمانی یک سالمند مشخص می‌نشیند. UI و API باید امکان بازسازی این تایم‌لاین را با یک کوئری ساده بدهند.
2. **Multi-tenant از روز اول.** هر مرکز (`Facility`) داده‌های مجزا دارد؛ حتی اگر فاز اول تک‌مرکزی فروخته شود، مدل داده باید بدون migration بزرگ به چند مرکز/چند نوع مرکز (خانه سالمند، مراقبت روزانه، مراقبت در منزل) گسترش پیدا کند.
3. **AI به‌عنوان لایه‌ی مکمل، نه رکورد اصلی.** خروجی‌های هوش مصنوعی (خلاصه شیفت، گزارش خانواده، هشدار ریسک) همیشه به رکوردهای منبع (`sourceRecordIds`) ارجاع می‌دهند و human-in-the-loop (تأیید/رد توسط مراقب) دارند — هرگز جایگزین قضاوت بالینی نمی‌شوند.
4. **قابلیت گسترش به Enterprise SaaS.** RBAC از ابتدا (نقش‌های Admin/Nurse/Caregiver/FamilyMember، و در فازهای بعد Doctor)، audit trail کامل روی هر تغییر رکورد بالینی (چون قابلیت حسابرسی/compliance حیاتی این حوزه است).

## ۲. استک فنی پیشنهادی (MVP)

| لایه | انتخاب | دلیل |
|---|---|---|
| فرانت‌اند + بک‌اند | **Next.js 14+ (App Router) / TypeScript** | یک codebase، سرعت توسعه بالا، SSR برای dashboard، API routes برای بک‌اند سبک |
| دیتابیس | **PostgreSQL** | داده‌های رابطه‌ای بالینی + نیاز به transaction قوی + JSONB برای فیلدهای منعطف (مثل `sourceRecordIds` در AIInsight) |
| ORM | **Prisma** | type-safety، migration ساده، مناسب تیم کوچک اولیه |
| احراز هویت | **NextAuth.js (Credentials + آماده برای OTP موبایل)** | مراقبان معمولاً با شماره موبایل/کد ورود کار می‌کنند نه ایمیل؛ ساختار باید از ابتدا OTP-ready باشد |
| UI | **Tailwind CSS + shadcn/ui + پشتیبانی کامل RTL/فارسی** | سرعت ساخت UI پزشکی/فرم‌محور، RTL بومی برای بازار ایران |
| اعتبارسنجی | **Zod** | schema اشتراکی بین فرم فرانت و API |
| فایل/تصویر (عکس سالمند، پیوست زخم و ...) | Object Storage سازگار با S3 (در ایران: ArvanCloud Object Storage) | جدا از دیتابیس، ارزان، قابل CDN |
| تولید محتوای AI (خلاصه شیفت، گزارش خانواده، تحلیل روند) | فراخوان API مدل زبانی از سرور (Next.js API route) — **synchronous، on-demand** در MVP | فاز اول نیاز به صف/queue ندارد؛ کاربر دکمه «تولید خلاصه» می‌زند |
| Background job (فاز ۲+) | BullMQ + Redis | برای هشدارهای زمان‌بندی‌شده (دارو فراموش‌شده، پایش روند شبانه) وقتی حجم داده بالا رفت |
| Deploy | ArvanCloud / سرور ابری ایرانی یا هر VPS با Docker Compose (Next.js + Postgres) | مطابق راهنمای build پروژه — بیلد سنگین فقط روی سرور SSH، نه داخل کانتینر توسعه |

> این فقط چارچوب پیشنهادی است؛ اگر تیم شما ترجیح دیگری دارد (مثلاً NestJS جدا برای بک‌اند، یا React Native برای اپ موبایل مراقبان)، مدل داده در بخش زیر مستقل از استک است و قابل پیاده‌سازی روی هر استکی است.

## ۳. نقش‌ها (RBAC)

- **ADMIN** — مدیر مرکز: مدیریت کاربران، شیفت‌ها، دیدن تمام سالمندان و گزارش‌های کیفیت
- **NURSE** — پرستار: ثبت دارو، علائم حیاتی، تأیید یادداشت‌های caregiver، مدیریت handoff
- **CAREGIVER** — مراقب: ثبت مراقبت روزمره (تغذیه، خواب، رفتار، حمام)، مشاهده تایم‌لاین سالمندان تحت پوشش
- **FAMILY_MEMBER** — عضو خانواده: مشاهده فقط‌خواندنی گزارش‌های تولیدشده + اعلان حوادث برای سالمند مرتبط
- **DOCTOR** *(فاز ۲)* — دسترسی به پرونده بالینی کامل + دستور دارویی
- تمام نقش‌ها به یک `Facility` مقید هستند (`User.facilityId`)؛ `FAMILY_MEMBER` علاوه‌بر آن به `Resident` خاص مقید می‌شود.

## ۴. جریان‌های کلیدی (Flows)

### Care Timeline (مفهوم مرکزی)
تایم‌لاین هر سالمند از **union** رکوردهای زیر ساخته می‌شود (نه یک جدول جدا، برای جلوگیری از دوباره‌کاری داده):
`VitalSign + MedicationAdministration + CareNote + IncidentReport + HandoffNote` — همه به `residentId` و `createdAt` مرتبطند و در یک کوئری/ویو مرتب‌شده نمایش داده می‌شوند.

### تحویل شیفت (Handoff)
۱. مراقب/پرستار در پایان شیفت رکوردهای آن شیفت را ثبت کرده
۲. سیستم دکمه «پیش‌نویس خلاصه با AI» را نشان می‌دهد → مدل زبانی از روی رکوردهای همان شیفت یک خلاصه تولید می‌کند (`HandoffNote.aiSummary`)
۳. مراقب خلاصه را ویرایش/تأیید می‌کند → `HandoffNote.content` نهایی می‌شود و شیفت بعدی می‌بیند

### گزارش خانواده (Family Report)
۱. به‌صورت دوره‌ای (هفتگی) یا درخواستی، از رکوردهای تایم‌لاین یک بازه، گزارش ساده‌فهم برای خانواده تولید می‌شود
۲. قبل از ارسال، توسط پرستار/ادمین تأیید می‌شود (`FamilyReport.approvedById`)
۳. سپس به پورتال خانواده / پیامک نمایش داده می‌شود

### هشدار ریسک (AI Insight — MVP ساده)
در فاز اول rule-based (آستانه‌های علائم حیاتی، دارو فراموش‌شده، افت مکرر تغذیه/خواب) + یک لایه‌ی خلاصه‌سازی LLM روی چند رکورد اخیر برای «چرا این هشدار مهم است». مدل‌های پیش‌بینی ML واقعی در فاز بعد با تجمیع داده طولی می‌آید.
